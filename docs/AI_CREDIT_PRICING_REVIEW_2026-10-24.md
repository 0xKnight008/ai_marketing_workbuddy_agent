## 2. 建议批准的计量规则

### 2.1 三档保留，统一成本换算，不再使用固定 1 / 6 / 20

| 档位 | 当前规则 | 建议规则 | 费率依据 |
| --- | --- | --- | --- |
| Eco | 1 credit / 内部步骤 | 实际有效 AI 成本换算，单个有成本的业务操作最低 1 credit | DeepSeek 当前配置模型的输入、输出、缓存及峰谷费率；人民币费用换算为美元 |
| Standard | 6 credits / 内部步骤 | 同一换算公式，不另加固定 6 倍系数 | Z.AI 当前配置模型的已核实账单费率；不能使用代码中的固定 $0.035 估算代替 |
| Flagship | 20 credits / 内部步骤 | 同一换算公式，不另加固定 20 倍系数 | 1Token 实际合同费率，配置为 LiteLLM 自定义成本并对账 |

建议公式：

```text
C = 一次业务操作中，产生有效、已保存结果的调用成本合计（USD）
结算 credits = C > 0 ? max(1, ceil(C × 1.20 / 0.001)) : 0
```

- `$0.001` 是内部成本预算，不是用户充值面值。不采用 R2 提出的面额转换。
- `1.20` 为公开说明的计量系数，用于成本波动、故障损耗等储备；不是承诺平台只赚 20%。
- 成本包括系统提示、历史、所选数据、正常的多轮检索/分析等实际供应商计费输入输出。系统故障重试不能直接转嫁为用户有效成本。
- 三档使用各自供应商费率，没有人为固定 1:6:20 倍率。因此不承诺每次 Eco 一定为 1 credit，也不承诺每次 Flagship 一定贵于所有 Standard 任务。
- 输入缓存命中按真实命中量计费。供应商已将推理 token 计入输出时，不再将 reasoning_tokens 重复相加。
- 金额及倍率使用整数微金额/定点运算。不能用 JavaScript 浮点误差造成多扣一个 credit。
- 不将本轮 $500 服务器或 $10,000 人员费用重复塞进每次模型的供应商 token 成本；它们保留在公司经营利润核算中。

### 2.2 已核实的 Flagship 示例

以下单价是用户已确认与 1Token 实际扣费一致的三条历史调用，仅作为新规则演示，不重算历史账单：

| 请求短 ID | 费用（USD） | 若分别为独立业务操作，按新公式结算 |
| --- | ---: | ---: |
| 072a78… | 0.0107985 | 13 credits |
| 18f25e… | 0.006696 | 9 credits |
| a778d1… | 0.0097885 | 12 credits |

这三次是调用，不一定是三个用户任务。如果属于同一业务操作，先合计 $0.027283，累计结算 33 credits，不能分别取整后收取 34 credits。

Eco 的 ¥0.87 / 158,364 tokens 是整批混合成本，不能推算出输入/输出分项费率，也不能推算每个用户任务应扣多少 credits。Standard 目前没有同等核实的计费样本。正式启用前，必须完成两条直连渠道的费率与账单核对；不发布没有依据的固定“典型价格”。

### 2.3 计费单位

- 用户工作台：一轮用户提交的生成请求为一个业务操作，持久化关联 task_id、message_id、operation_id。
- 报告：一次明确请求的报告生成/新版本为一个业务操作。
- 导入/分类/主题：一次用户请求对应一个父操作；内部批次、分块及 LLM 调用属于子记录。
- 自动发布：生成阶段作为明确的业务操作记录；AI 费用与发布 task/API 费用分别显示，不能把审核点击作为新的 AI 扣费。
- 普通数据库导入、打开报告、核对证据、点击审核本身不消耗 AI credits；请求 AI 分析/修改结果时才产生新的估价。
- 每个父操作累计有效成本后取整。若已有有效子结果持久化，则按累计成本的结算值减去已结算值追加记账，避免每步重新最低扣 1 credit。
- 同一 operation_id 的重复回调、网络重发、worker 重领不能成为新付费操作。用户明确发起的新一轮或新版本才创建新计费单位。

## 3. 用户流程：仍然最多三步

1. 导入/选择数据。
2. 确认目标：对话框右下角选模型，发送区展示预计 credits 和最高预算；提交同时确认该预算，不增加一个常规必经页面。
3. 输出结果：展示请求档位、实际执行模型/档位、实际结算、释放的预扣，以及任务结果。

示例文案，仅用于说明展示方式，不是模型固定报价：

```text
预计使用 8–13 credits，本次最多 15 credits。
[开始任务，最高 15 credits]

完成 · Flagship · 实际使用 11 credits · 已释放预扣 4 credits
```

- 估计值、最高预算与实际扣费必须分别标明。预扣不是已结算消费。
- 输入、目标、模型变化后重新估价。报价建议有效 10 分钟；过期或估价条件改变须刷新并重新确认，不沿用失效授权。
- 余额不足时展示保留模型充值、明确同意换档、缩小范围等选项，不静默降低模型能力。
- 任一调用开始前，校验剩余预算及输入/输出上限；无法在已确认上限内完成时，保存当前进度并暂停。不能先发生大额费用，再要求用户接受超额账单。
- 用户确认的预算是当前操作硬上限。供应商异常超收由平台记录、告警和处理，不对用户事后追加未授权 credits。

## 4. 报价、预留、结算、退款

### 4.1 报价和预留

- 服务端根据完整上下文、模型费率、所需阶段和输出上限计算报价；不信任前端传入的成本、余额或费率。
- 未知的缓存命中按未命中报价，执行后按实际使用结算；人民币费率需记录汇率快照，不能每次用新的即时汇率重算旧操作。
- 预留用户确认的最高 credits，并锁定报价/计价版本。并发任务在同一余额锁内预留，不能超卖同一份余额。
- 保留原有资金来源顺序：剩余试用额度 → 当期套餐额度 → 充值额度。每一部分的金额、账期、来源均记录。
- 已订阅试用账号不足覆盖报价时，沿用现有订阅付款交接；未订阅账号不能因此自动变为已付款状态。

### 4.2 成功及部分完成

- 持久化有效结果时，累计结算实际 credits，释放尚未消耗的预留。释放金额按原资金明细归还。
- 继续保留 PR #114 的边界：已经保存且可以复用的有效分类/检索/结果片段，后续步骤失败时仍可保留相应消费；未产生有效结果的部分退款。
- 部分完成必须在 UI 明示已保存内容和对应费用，不能把“部分结果已收费”隐藏成“整个任务失败，消费 0”。
- 用户拒绝有效内容、或 AI 已完成后外部发布失败，不自动抹掉已完成 AI 生成费；发布失败不额外扣成功发布 task。
- 退款、预留释放、实际扣费是不同事件，业务流水中明确区分。原始账项不可覆盖。

### 4.3 失败和对账异常

- 无有效结果的最终失败释放全部未结算预留；不同资金桶和历史账期保持原退款语义。
- 系统故障重试不向用户重复收费；已发生的供应商账单仍记录为平台实际成本。不能因用户退款而把供应商真实支出清零。
- 保留真实 paid retry 的成本记录和失败率监测，设置失败支出预算与熔断，防止“全部退款但无限付上游费用”。20% 储备不是无限重试授权。
- 缺失 usage 不等于 0 tokens/0 成本。先进入待对账状态，不使用旧 1/6/20 作为未验证的结算兜底，不重复调用来补收据。
- 建议待对账预留最长 24 小时，超时未能取得可验证费用时释放未核实部分，由平台承担损耗；迟到的上游账单不能再未经同意补扣客户。
- 结果重复送达、退款回调重试、跨月处理、worker 崩溃和回放均要求幂等。

## 5. 成本防护同步调整

### 5.1 AI 和充值

- 当前代码同时使用固定 `supplierCostMicros`（Eco $0.002、Standard $0.035、Flagship $0.15）和固定 1/6/20 扣费，均不能作为新版最终实际成本。
- 含量与充值 credits 都应对应可执行的 AI 预算。充值必须同步增加它所支持的预算，不能钱已付但被旧 $6/$20/$55 月度供应商估算门槛阻断。
- 拆开 AI 预留/已结算预算、渠道成本、其他付费 API 预算。对运营设置的额外硬上限，必须事前展示，不能伪装成模型额度不足。
- 当前配置的输入/输出上限需要落实到每条真实请求的校验和供应商输出参数，而不是只在生成后做近似长度校验。推理模型的输出上限应包含其计费推理输出。
- 费率或模型变更采用版本发布，不在当前任务执行中悄悄更新倍率。

### 5.2 Zernio

- 当前代码常量 `150_000 micros` 等于 $0.15/account/month，须改为运营预算 $1/account/month。
- 按同一上游团队聚合，公开阶梯：前 2 个免费；3–10 各 $6；11–100 各 $3；101 起各 $1。
- 超过 100 个账号且整月保持连接时，全平台费用为 `账号数 × $1 + $218`。$218 差额全平台只计一次，不能每个工作区重复收取；工作区内部预算与公司上游实际成本分开。
- 上游账单按天折算。需记录连接/断开时段并定期对账；不要用月末瞬时连接数冒充整月已付费用。初版可用保守预算，必须与真实账单明确区分。
- X API、短信、电话、超额消息/广告等另有按量费用，不包含在 $1 连接成本内，也不自动挪用 AI credits。现有套餐未授权的额外付费能力不因本次改价自动开启。

## 7. 数据库影响：需要增量持久化

这不是只改 UI 或三个常量。建议增加持久化模型，具体表名及下一可用迁移号在同步 main 后确定：

| 数据 | 最少需要持久化的信息 |
| --- | --- |
| 报价 | workspace、业务操作、请求档位、计价版本、估计、最高 credits、有效期、确认记录 |
| 模型费率快照 | 供应商、wire model、币种、输入/输出/缓存费率、峰谷条件、汇率、有效时间；无密钥 |
| 请求收据 | 子请求唯一键、父操作、实际模型、token 分项、有效结果/故障归属、可验证成本、证据来源及对账状态 |
| 资金预留 | 试用/套餐/充值来源、账期、计价版本、预留上限、已结算、已释放及处理状态 |
| 结算与调整 | 累计有效成本、目标累计 credits、差额事件、原账项引用、幂等键及审计原因 |
| 成本对账 | 上游费用、已记录费用、失败损耗、异常标记、计价版本差异 |

- 保留 PR #106/PR #114 的既有数据及接口能力。新增 SQL 使用增量迁移，不能改写已经部署的 0039 迁移。
- 当前 token ledger 的 `event_id` 不能单独证明供应商请求全局幂等；`run_id` 也不能单独区分同一任务中的多轮用户消息，需要明确父子操作键。
- 0039 的单一退款引用约束不能未经分析就复用到“部分释放 → 之后失败退款”的多事件流程。新设计必须保证总释放/退款不超过原预留及相应资金来源，不能只删除唯一索引解决。
- 财务记录不能随着任务被用户隐藏/删除而级联消失；新表保留工作区隔离、RLS、内部服务鉴权。
- 跨 Runtime LibSQL 和 Platform PostgreSQL 无分布式事务保障，必须有持久化交付/补偿和对账，不能仅靠一次 HTTP 回调。

## 8. 历史数据和上线切换

- 原有可用余额、试用 carryover、预扣和拒付债务不做倍数换算，不按新公式重算历史消费。
- 历史账项、现金实付、有效期及来源账期保持；新旧规则通过计价版本区分。
- 保留历史小数余额；部署、退款、回放和迟到回调均须幂等。
- 充值退款继续按原充值记录及兑换比处理；推荐奖励、token 数、现金及 task quota 不变。
- 切换前在途操作锁定旧版本；新操作在展示并接受新报价后使用新版本。旧 worker/回调不能使用新规则重扣。
- 已购买 credits 的新消费方式须通过清楚的提前通知及首次新规则确认，不将确认本文件等同于所有客户已接受变更。
- 先在非收费的影子计量中对比真实调用与账单，再受控启用新结算。供应商价格未核实或收据链路不完整的模型不得进入新计费模式。
- 保留版本开关，回滚只停止新版本报价并处理在途预留，不改写已结算的新旧账本。
- 本次不变更 Stripe 月/年订阅 Price ID，不做推荐奖励降为 10% 的迁移。

## 10. 确认后 build 的验收门槛

1. 三档各覆盖成功、长上下文、多步骤、缓存命中、推理输出、缺失 usage；整数边界验证不多扣。
2. 多个子调用只按累计有效成本取整；持久化有效部分后的最终失败只退未结算部分。
3. 并发预留、重复回调、worker 崩溃、重复退款、部分释放后再次退款、跨月、退款后显式重试不重复记账。
4. 混合试用/套餐/充值资金及 Stripe 交接回归；未付款、不足额、试用过期、充值拒付不绕过权益限制。
5. 已确认预算不能被后续多轮请求或模型变化突破；不静默降档；额外付费 API 不意外启动。
6. task、报告、导入、主题、自动发布链路都使用一致规则；发布 approve/reject 与有效结果留存继续正常。
7. Playwright 覆盖 en/zh/es 用户流程，以及中英 admin/token ledger、CSV、手机尺寸与余额显示。
8. Zernio 阶梯计算/按天预算、AI 真实费率、缺收据处理及充值后可继续执行有独立验证。
9. 完成模拟/测试数据库验证后，再由运营明确控制三档真实小额验收。供应商生产账单核对不能由 stub 测试代替。
10. 新旧计价切换覆盖余额、试用、已用量、预留、退款、拒付债务、月度重置及回滚；所有余额及现金数值不进行面额换算。
